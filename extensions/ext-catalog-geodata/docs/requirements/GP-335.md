  - A person without a grant on a layer receives a 403 or an empty answer from WMS and WFS, and receives the data once the layer is shared with them or with one of their groups.
  - A data rule with an area, a CQL row filter or hidden columns changes WFS answers accordingly, and the same holds for the same person through AuthKey.
  - After every rewrite the rules read back from GeoFence match the generated set, including column lists and areas, and a mismatch is reported instead of being ignored.
  - A rule added by hand in GeoFence disappears at the next rewrite of the organization's rule set.

Permissions on resources and data rules (area, rows by CQL filter, hidden columns; see GP-308) are
translated into GeoFence rules per person and per role. Geoportal rewrites the whole rule set of an
organization every time, with priorities it decides, and nobody edits rules in GeoServer by hand: a
set written piecemeal by several hands soon becomes unreadable. GeoServer has no users of its own: the
person's name comes from the gateway or from AuthKey, and the roles from a JDBC role service on views
of the Geoportal database. Known traps from the F0 proofs: both paths must read roles from the same
source, the authentication cache must be short enough for revocation, and GeoFence 2.28.5 silently
drops column lists sent as JSON and areas sent as XML, so every rule is written in the format that
keeps it and read back.
