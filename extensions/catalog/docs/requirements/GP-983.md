  - The extension `ext-catalog-geodata` (manifest id `dev.geoportal.ext.catalog.geodata`) holds the loading into PostGIS and Cloud Optimized GeoTIFF, GeoServer and GeoFence, publishing, data rules, the gateway and the proxy for OGC services, with its own schema.
  - It declares `ext-catalog` and `ext-catalog-connection` as required dependencies (MK-132) and adds its kinds to them through their contracts (MK-134); a geodata dataset is a file of the file manager with a geospatial preview, and a PostGIS table is a part of a PostgreSQL connection that offers the use "map".
  - An installation with `ext-catalog` and without `ext-catalog-geodata` manages files and connections; the geodata datasets appear with the placeholder of an absent extension (MK-135).
  - The end-to-end suites of loading, publishing, GeoFence rules and the gateway pass with `ext-catalog-geodata` installed next to the extensions of mosaikit-ext.
---

The catalog extension of today mixes two things: a manager of files and connections that any product
needs, now `ext-catalog` and `ext-catalog-connection` of mosaikit-ext, and the geospatial part that is
Geoportal's own. This requirement splits the second out as `ext-catalog-geodata`: PostGIS and COG
loading (GP-936, GP-937), GeoServer and GeoFence (GP-334, GP-335), publishing and the lifecycle of
layers (GP-114, GP-118), data rules (GP-308, GP-309), the gateway and AuthKey (GP-336), the proxy for
OGC services (GP-939, GP-297), extent and reference systems (GP-321, GP-324), RNDT metadata and the
public catalog (GP-338). The schema `ext_catalog` and its migrations go with it. No code moves until
the extensions it builds on exist; MK-131 to MK-135 (libraries in extensions, required and optional
dependencies, presence, contracts, references that degrade) are what makes the split possible.
